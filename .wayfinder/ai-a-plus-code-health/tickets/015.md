## Question

정적 사실·문맥 검색·구조화 review·근거 상태·승인형 runtime feedback 중 무엇을 기본 core로 남기고 자체 독립 기여를 한 곳에 어디에 둘 것이며, 이를 유지하거나 폐기할 최소 same-budget baseline·ablation arm과 단일 판정 기준은 무엇인가?

## Resolution comment

core 구성의 효과는 여섯 누적 arm을 인접 단계끼리 비교한다. 제품 경로를 여섯 개로 만드는 것이 아니라 평가할 때만 같은 pipeline의 기능을 하나씩 켠다.

| Arm | 구성 | 확인할 추가 기여 |
|---|---|---|
| A | raw diff 또는 사용자 seed source + 일반 LLM review 1회 | 비교 기준 |
| B | A + fixed-five 구조화 review | 다관점 구조화 |
| C | B + AST·symbol·import·lexical | 정적 fact |
| D | C + 최대 2-hop Code Graph | graph 문맥 |
| E | D + HypothesisContract·근거 상태 | 반증·근거 계약 |
| F | E + 승인형 동적 검증 DAG | runtime feedback |

각 기술의 기여는 `B-A`, `C-B`, `D-C`, `E-D`, `F-E`로 계산한다. 함수 단위 CFG·def-use는 core arm에 섞지 않고 적합한 함수에서 `F`와 `F+CFG`를 별도 실험한다.

### 동일 예산 조건

- 같은 case split과 source snapshot
- 같은 model/version과 sampling 설정
- 같은 총 token·tool-second·wall time 상한
- 같은 retry 제한과 출력 schema
- 쓰지 않은 예산을 다른 자원으로 바꾸지 않음
- 파일럿 뒤 arm을 동결하고 final holdout에서 다시 실행

### 단일 유지 판정

인접 arm 대비 아래 하나를 충족해야 core에 남긴다.

1. 사전 등록한 목표 품질 지표가 **5%p 이상 개선**
2. 품질 guardrail을 지키면서 token 또는 시간이 **10% 이상 감소**

두 경우 모두 Critical/High Recall 기준을 지키고 추가 unsafe·unsupported 주장이 없어야 한다. 실패한 구성은 core에서 제거하고 `experimental` 또는 `excluded`로 내린다.

파일럿은 arm·예산·threshold를 고정하는 예비 결과다. 독립 기여와 우월성 주장은 frozen final holdout 결과만 사용한다.

기계 판독 가능한 적용값은 [현장 입력 명세 v13](../field-input-manifest.yaml)의 `core_ablation_contract`에 고정했다.
