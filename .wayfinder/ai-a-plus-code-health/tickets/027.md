## Question

어떤 결과를 입증해야 사용자 목표인 "작은 모델을 태운 전체 시스템이 강한 모델의 단일 진단보다 문제를 더 잘 찾고, 그 모델이 놓치는 문제도 발견한다"를 충족하는가? 호출 비용과 동적 실행 안전은 어떻게 분리하는가?

## Resolution comment

평가 목표를 모델 자체의 서열이 아니라 **작은 모델을 사용하는 전체 진단 시스템의 문제 발견 효과**로 정정했다. v23에서는 봉인된 같은 80사례에 강한 모델 1회 진단 `S_strong_single`과 작은 모델만 사용하는 전체 시스템 `F_runtime_feedback`을 추가로 짝지어 비교한다. 사례마다 독립적으로 봉인한 모든 결함을 분모로 발견률(Recall), 중요 결함 발견률, 정밀도, 강한 모델만/시스템만 찾은 결함과 유형별 누락을 계산한다. 가족 단위 bootstrap 95% 신뢰구간에서 시스템 발견률 차이의 하한이 양수이고 중요 결함 발견률·정밀도·부당 기각 안전 조건을 지켜야 우월성을 주장한다. 사례당 단일 권고율만으로 "더 많은 문제 발견"을 주장하지 않는다.

같은 저장소 스냅샷·과제·소스 범위·결과 형식·20분 및 전체 토큰 한도를 적용한다. 단일 모델에는 구조 검색·실행 도구를 붙이지 않으며, 이는 **제품 구성 비교**이지 동일 모델 자체의 성능 비교가 아니다. 작은 모델의 계획·다섯 관점·병합·재시도 등 모든 운영 호출과 캐시 토큰을 포함한 실제 API 청구 금액, 전체 금액 및 독립 검증된 참양성당 비용을 공개한다. 비용 절감을 따로 주장하려면 실제 청구 근거로 입증한다. 두 모델·별도 계열 평가 모델·가격·프롬프트·평가 자료는 최종 출력을 보기 전에 고정한다.

기존 A~F 여섯 군은 같은 작은 모델로 인접 요소의 기여를 검증하는 별도 평가로 유지한다. 과거 A~F +30%p/신뢰구간 관문은 없애지 않는다. 공식 기준은 특정 모델 크기나 80사례를 요구하지 않으며, 이는 프로젝트가 미리 정한 검증 계약이다. 자원 한도를 품질 KPI로 내세우지 않는다. 다만 승인형 외부 코드 실행을 제거한다는 결정은 아니므로 현재 WSL에서 한도가 강제되지 않는 실행을 허용하지 않는다. 안전한 실행 환경이 없으면 해당 기능·F 군·우월성은 미입증으로 남긴다.

`src/modules/evaluation/paired.py`는 여섯 군 동일 모델의 사례당 권고 하나를 처리하고, `src/modules/evaluation/head_to_head.py`는 새 두 모델/복수 결함/신고 API 비용의 **봉인 입력 오프라인 집계**를 처리한다. 후자는 시험용 자료의 누락·오탐·비용·독립 판정 경계까지만 확인됐다. 실제 모델 호출, 원본 영수증, 독립 평가 자료 생산·판정은 구현/실행되지 않았으며 v23 명세와 시험 결과만으로 우월성을 주장하지 않는다. 당시 두 모델의 버전·가격·숨긴 정답·실제 실행 결과도 없었으며, 후보 버전 지정과 구독형 OAuth 비용 제약은 [028](028.md)에서 별도로 기록한다.

**v26 개발용 실행 예외(최종 평가 조건은 유지):** 소유자의 후속 결정으로 cgroup 제한이 강제되지 않는 rootless Docker도 정확한 RunManifest 직접 승인을 받은 개발용 대상 실행에 허용한다. 요청한 CPU·메모리·PID 수치를 실제 제한으로 주장하지 않고 경고한다. 이 티켓의 금지는 **최종 F·A+ 인증 증거로 그러한 실행을 합산하는 것**에 계속 적용한다([진행 029](029.md)).
