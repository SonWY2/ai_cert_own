## Question

본인 계정의 Codex OAuth 인증·양쪽 모델 접근이 가능한 뒤 어떤 동결 사례와 독립 증거로 `S_strong_single` 대 `F_runtime_feedback`의 실제 발견률·고유 발견·실제 API 비용을 비교하는가?

## 현재 확인 및 남은 외부 전제조건

- 소유자의 로그인 뒤 `openai-oauth@2.0.0`이 루프백에서 기동했고, 강제 `--models` 없이 `/v1/models`에서 `gpt-6-sol`·`gpt-6-luna`를 확인했다. `/v1/chat/completions`의 소스 없는 호출은 두 모델에서 500 `Bad Request`였고, `/v1/responses`에서는 둘 다 정상 응답했다. 승인형 클라이언트도 Responses로 교체했다. 같은 비소스 요청을 해당 코드로 보낸 결과 양쪽 모두 `{\"ready\":true}`, 입력 31·출력 9·캐시 0토큰, 응답 1.534초/1.459초였다. 이는 연결 확인이지 진단 성능 차이가 아니다.
- 각 전송 소스에 대해 Git SHA·모델·전송 범위를 포함한 정확한 RunManifest와 소유자의 대화형 일회용 승인이 필요하다. 이 일반 대화는 프로젝트가 요구하는 manifest 해시 승인을 대신하지 않는다.
- 최종 80개 숨긴/시간 분리 사례와 독립 oracle·판정 모델, 작은 모델의 실행 피드백 포함 전체 F 경로, 격리 실행 CPU/메모리 한도를 강제하는 호스트가 아직 없다. 승인된 개발 심볼 호출은 아래에 기록했으며 최종 실증을 대신하지 않는다.
- OAuth 구독 경로에서 제공자별 실제 USD 청구 영수증이 나오지 않는다. 토큰·소요시간 파일럿은 가능하지만 `billed_micro_usd` 최종 비교는 독립 제공자 청구 증거가 생길 때까지 불가하다.
- 비인증 루프백 서버는 소유자가 승인한 개발용 두 모델 호출 동안에만 다시 기동하고 호출 후 종료했다. 상시 켜두지 않는다.

소유자가 두 입력의 해시를 직접 입력한 뒤 동일 Git 개발 사례·동일 `page` 문맥에 대해 강한 모델 1회 기준선과 작은 모델 5관점 정적 진단을 각각 호출했다. 강한 모델은 결과 검증에 실패했고 작은 모델은 개발 결함의 후보를 반환하지 않았다. 개발 사례 결과는 final holdout 주장에 포함하지 않는다.

- 원본은 `build_dev_fixture.py --mutation correctness`가 생성한 개발용 Git SHA `630f777997abf640c8e41981259d49b70935ae4c`. `oracle.py`를 새 복사본에서만 제거한 진단 입력은 `/tmp/wreckfish-oauth-pilot-20260926-source-only`, SHA `e2028838757f1df99a23f8b4aa51b0e73711c87d`. 출처 봉인 경로는 `/tmp/wreckfish-oauth-pilot-20260926-source-only-bundle/runs/573c2e1ce7f958c9a7cb8996ff868edf1e8c49d9eb812eb2c2648bd76174a97e`; `--symbol page`의 노드는 8개·소스 조각 2,461바이트이며 oracle은 포함되지 않는다. 원본 사례와 새 SHA는 최종 숨김 자료가 아니다.

- 승인 결과는 단일 선택 심볼 개발 파일럿뿐이다. 작은 모델 5관점은 실행 피드백 없는 정적 진단이므로 최종 `F_runtime_feedback`이 아니다. 두 호출에서 모델 사용량은 기록됐지만 강한 호출의 가설 결과가 유효하지 않고 원본 USD 청구·독립 최종 oracle도 없어 발견률·비용 우월성을 보고하지 않는다.

- 강한 1회 실패로 유효한 양군 가설 비교는 불가능하다. 재호출은 소비한 승인을 재사용할 수 없으며 소유자의 새 정확한 RunManifest 승인이 필요하다. 최종 80개 봉인 사례, 실행 피드백·독립 판정·API 청구액은 모두 미확보.

## 추가 점검: 재현 결함과 실증 경계

- 독립 경계 검토 뒤 Git `refs/replace`가 동결 blob 내용을 바꿔도 스캔·재인증이 이를 수락하던 문제를 임시 Git 사례로 재현해 교체 객체를 비활성화했다. `--clean-replay --symbol` 조합의 `NameError`와 패키지 `__init__.py` 변경 영향 누락도 각각 재현·수정했다. 비UTF-8 Git Python 파일명은 증적·그래프가 지원하지 않으므로 명시적으로 전체 스캔을 거절한다.
- 진단 CLI의 미지원 모델 선언·출처 묶음 내부 영수증/실행 출력·Git에 없는 실행 파일이 영수증 소진 전 차단되도록 고쳤다. 전체 Git Python 모듈을 한 번에 전달하는 개발용 `--scope full --single-baseline`을 추가했고 파싱 누락은 승인 전에 거절한다. 시험용 입력의 Python 3.12.4/3.14.3 전체 회귀 각 148개 통과. 실제 정적 `scan_sources.py --clean-replay --symbol`·`plan_scan.py candidate --scope impact`, 부적합 모델 진단 CLI 거절과 시험용 응답의 전체 범위 CLI 호출 기록 1개를 별도 확인했다. [원자료 범위와 명령 결과](../../../docs/evidence/03-ai-pipeline-technical-design.md)는 개발 검증이며 대상 실행/실모델 진단·최종 평가가 아니다.
- 이 티켓은 계속 `open`이다. 개발용 영수증 두 개는 발급·소비됐고, 강한 모델의 실제 단일 심볼 출력은 실패했다. 전체 범위 강한 1회 기준선은 여전히 시험용 입력에서만 확인했다. 실행 피드백을 포함한 작은 모델 전체 F는 연결되지 않았다. 신규 전송·실행의 수동 승인, 강제 cgroup 호스트, 숨긴 독립 80사례·다른 계열 판정·제공자 원본 USD 청구, 회사 업무 근거·수정 제안서 공식 수용 없이는 최종 우월성이나 A+을 선언하지 않는다.

## 개발용 진단·실행·리포트 연결 결정

- 기존 선언형 RunManifest의 workload를 승인 소비 직후 한 번 실행하고, `verify_execution`으로 원본·manifest·로그를 대조한 **미인증 관측**만 모델에 전달한다. 이는 개발 연결 검증이지 동결 manifest의 최종 가설 기반 검증 선택·독립 근거 판정 순서를 바꾸는 결정이 아니다. `log`·`evidence` 전송 선언과 자원 강제 Docker 사전 확인이 없으면 소유자 영수증 사용 전에 거절한다.
- 모델 응답 실패는 원인 코드·토큰·관점 상태를 구분하며 불완전 종료는 코드 3으로 보고한다. `check_code.py`는 저장소와 재사용 manifest를 받아 새 source·manifest·승인·최종 5종·Markdown을 연결한다. 마크다운은 검증된 봉인의 파생 표현이며 실행 실패를 Finding 확증으로 승격하지 않는다. 프롬프트 해시 `5402e3628a4c6256a2cfc632b97dc52ea32b467e2534e198ba28662718b2accb`는 이전 소유자 승인 두 건과 호환되지 않는다.
- Python 개발 환경 `python3 -m unittest discover -s tests -q` 160개 통과. 임시 Git·시험 전용 승인/응답에서 단일 CLI 리포트(관점 완료 5, 후보 0, 확증 0)를 직접 확인했고, 비대화형 실명령은 모델·실행 전에 코드 2로 거절됐다. 시험용 실패 trace의 모델 전달·명령 비정상 종료 표시·로그 변조 거절은 확인했지만 실제 대상 실행이나 실제 신규 모델 출력은 확보하지 못했다.
- 강한 `S_strong_single` 대 작은 전체 시스템의 동일 예산 결함 단위 비교, 같은 작은 모델 6군 기여 검증, 숨긴 80사례·독립 oracle·실제 USD 청구 증거가 다음 관문이다. 현재 WSL의 cgroup 제한 부재, 개발 대상 고정 의존성 이미지와 신규 소유자 승인이 없는 동안 일곱 개발 사례의 새 CLI 실모델·실행 정확도도 미검증이다. 실패 결과를 재시도로 숨기거나 개발 결과를 최종 성과로 합산하지 않는다. 티켓은 `open` 유지.

## 공개 as-is/to-be 비교 시도(2026-09-26)

- 사용자가 요청한 일반 단일 프롬프트 `A_plain_llm`과 강한 모델 1회 `S_strong_single`을 구분했다. 현재 `--single-baseline`은 5관점 공통 프롬프트를 1회 쓰므로 일반 `A_plain_llm` 실측으로 재분류하지 않는다. 전체 F도 선택 실행·독립 판정까지 연결되지 않았다.
- 직접 고정·스캔한 공개 후보: [Prefect #23207](https://github.com/PrefectHQ/prefect/issues/23207) 수정 전 `148e99781fb05df258d3efddb5ef4fee0b61c9f2` Python 1,912개(출처 ID `9c8760370d6f5fba4e30a404ce3612445f3eef1daf05307386ce1ce6a841d1cf`); FastAPI Users v15.0.5 `9ef8cd82619856772ac06a178b114eb47c79586c` Python 88개(출처 ID `760e1535202fffae09d7209c1f6e9f9a53b51d6f14e67c4c4b3fd7be347ca9ca`). Prefect의 공개 보고·수정은 개발용 정답 후보일 뿐 숨긴 독립 사례가 아니다. [실행 명령·원자료·비교 경계](../../../docs/evidence/04-public-as-is-to-be-comparison.md).
- 이번에 수행한 것은 불변 Git 정적 스캔과 결함 심볼 문맥 조회다. 신규 실모델 진단·대상 코드 테스트/프로파일러·독립 평가·실제 USD 청구 확인은 **0건**. 두 기존 영수증은 소비됐고 새 승인 영수증이 없으며 루프백 프록시는 현재 미기동. 기록된 WSL Docker 자원 강제 실패, 대상별 이미지·숨긴 독립 80사례·청구 영수증 부재도 계속 차단 조건이다. 공개 스캔을 성능 우월성이나 A+ 충족으로 주장하지 않는다. 티켓 `open` 유지.

## 실제 결함 사용 및 Docker 실행 요청 재판정(2026-09-26)

- 인위적 결함 주입은 필수 아님. [Prefect #23207](https://github.com/PrefectHQ/prefect/issues/23207) 수정 전 원본 SHA `148e99781fb05df258d3efddb5ef4fee0b61c9f2`와 [병합 수정 #23208](https://github.com/PrefectHQ/prefect/pull/23208) SHA `cf45751fd8e82ca784821fdc2cee5f2cdc6b0746`를 그대로 비교 후보로 쓴다. 수정 후 Git을 별도로 가져와 정적 스캔했다(출처 ID `d51d9262d77adff8a510a498eb2e5fc0fa4090fabbd9c625b2775268df48dec3`, Python 1,912개). 원 보고·수정·테스트가 공개돼 있으므로 개발용 oracle이지 숨긴 최종 정답이 아니다.
- 당시 선택 Docker 컨텍스트는 `rootless-wreckfish`였고 cgroup driver `none`으로 CPU·메모리 제한이 강제되지 않았다. rootful `dockerd`는 시스템 경로에 없었고 `sudo -n true`는 암호 요구로 실패했다. **당시 v25의 승인형 대상 실행 CLI는 자원 강제 불가를 사전 거절했다.** 대상별 새 승인 영수증도 없었다. 이후 개발용 실행 허용으로 바꾼 v26 결정은 아래에 별도로 기록한다.

- **작게 시작해 실패하면 중단한다.** 먼저 기존 `build_dev_fixture.py`의 정상·6개 개발 변이와 공개 Prefect 수정 전/후를 사용한다. 원래 동작 계약·회귀 검사 또는 원본/변이/수정본의 `통과 → 실패 → 통과`가 성립한 경우만 개발용 oracle로 보존한다. LLM은 다양한 테스트와 경계 사례를 **제안**할 수 있지만 LLM 단독 판정·단일 템플릿의 다수 변형을 독립 정답이나 최종 80사례로 세지 않는다. 발견 결과를 본 뒤 테스트를 바꾸지 않는다.
- **진단과 판정을 분리한다.** 같은 Git SHA를 대상으로 먼저 `--static-probes`의 실행 없는 위험 가설을 수집한다. 실제 모델 비교는 같은 사례·시간·토큰 상한에서 동일 작은 모델의 정적 반례 입력 유무를 맞추고, 강한 단일 모델도 별도 비교한다. 구조화 문맥에 호출 그래프가 포함돼 있으므로 정적 반례 단독 기여를 주장하려면 그래프 문맥은 양군에 똑같이 주어야 한다. 이미 동결된 C/D/F 정의를 몰래 바꾸거나 이 개발 비교를 최종 A~F 성과에 합산하지 않는다. 의미가 있는 경우 다음 manifest의 실험 후보 교체 규칙을 따라 재동결한다.
- **자동 수집은 아직 구현되지 않았다.** 현재 `src/evaluate_cases.py`는 평가자가 별도 봉인한 기록의 무결성과 집계만 검사한다. 실제 모델 호출, 원시 사용량·청구서 수집, 행동 oracle 수행, 다른 계열 판정 모델의 익명·순서 섞기, 서명키 분리, 결과 전 선행 동결을 하는 생산 경로가 없다. 최소 추가 작업은 이 입력을 만드는 격리된 수집 경로이지, 긍정적 수치를 채운 가짜 평가 JSON이 아니다. 예산 초과·모델 실패·정상 사례의 거짓 경보까지 빠짐없이 기록하고 원자료·해시·명령을 사용자 보고서에서 재생 가능하게 잇는다.
- **수작업을 없앨 수 없는 부분:** 현재 RunManifest는 정확한 소스·모델·전송 범위당 소유자 일회용 승인을 요구한다. 일괄 승인으로 바꾸려면 사전에 정확한 사례와 권한을 동결하는 정책 변경 및 소유자 동의가 필요하며 에이전트가 대신 승인할 수 없다. 평가 키·숨긴 정답을 진단 시스템과 분리한 자동 판정은 사람 판독을 줄이지만, 같은 작성자가 모든 역할을 수행하면 외부 독립 평가라고 주장할 수 없다. OAuth 구독 토큰은 실제 USD 청구가 아니고, 회사 업무 사례·기획서 수정 수용·최종 안전 실행 조건은 자동 생성 불가하다.
- 개발 경로에서 미달성이 확인되면 사례/프롬프트를 성공 때까지 바꾸어 최종 수치로 세지 않는다. 잠재력 확인 뒤에만 동결된 80개 숨긴·시간 분리 사례, 같은 작은 모델 A~F, 강한 단일 모델과 F의 결함 단위 결과·독점 발견·비용, 95% 신뢰구간을 **별도** 수행한다. 공식 A+는 이 자동 집계 자체가 아니라 제안서 달성·사용 가능한 시스템·업무 적합성·AI 선택과 최적화의 실제 효과를 심사자가 확인해야 한다. 티켓 `open`, v26 주장 경계 유지.

- 사람 평가를 했다고 쓰지 않는다. 별도 판정 모델의 실제 판정 기록이 확보된 결과에 한해 **“사람의 평가를 대신해 LLM 판정을 활용했다”**고 밝히고, 판정 모델·입출력 근거·실패 및 독립 검사 우선순위를 함께 공개한다([정확한 표기 계약](../../../docs/evidence/01-kpi-measurement-framework.md#finding-정답)). 현재는 판정용 실모델 평가 자료가 없으므로 해당 문구를 완료된 프로젝트 성과로 사용하지 않는다. 이는 기존 v26의 무인 판정 경계를 명확히 적은 것이며 티켓 `open` 유지.

## 반복적인 마지막 관점 예산 보류의 원인 수정

- 기존 `analyze()`는 매 관점에서 요청 JSON의 UTF-8 바이트 수와 256을 새 입력 토큰으로 예약했다. FastAPI 자유 탐지에서는 실제 네 관점 합계 20,274토큰을 쓴 뒤에도 잔액 19,726이었지만 마지막 요청의 바이트 예약 때문에 보류됐다. 중복 해시 제거만으로는 다른 문맥에서 같은 문제가 반복될 수 있다.
- 첫 관점은 원래의 보수적 바이트 예약을 유지한다. 이후 같은 `analyze()` 호출 내의 관점은 직전에 제공자가 보고한 **입력·캐시 입력 토큰의 합계 + 양쪽 관점명 바이트 수 + 256**으로 사전 예약한다. 제공자 사용량의 입력 0·누락/무효·승인 잔액 초과는 실패·중단하고, 동일 총 토큰 한도·출력 상한·사용량 사후 검증을 유지한다. 문맥이 다른 다음 모듈에서는 이전 관점의 측정치를 사용하지 않는다.
- FastAPI의 **수정 전 기록만을 이용한 재계산**에서는 네 번째 관점의 전체 5,126토큰을 전부 입력으로 보더라도 다섯 번째 예약 상한 5,398, 당시 잔액 19,726에서 여유 최소 14,328이다. 실제 다섯째 호출·추가 발견을 관측한 것은 아니다. 제공자 입력 계산이 바뀌거나 실제 예산이 부족하면 보류·사후 실패는 여전히 가능하다. 합성 문맥 7,000토큰 회귀는 수정 전 네 관점 뒤 보류를 재현하고 수정 후 다섯 관점 호출을 확인했다. 입력 0 또는 실제 한도 초과 보고는 뒤 관점을 차단했다. Python 3.12.4 회귀 **168개 통과**, Python 3.14.3 **168개 실행(167개 통과·1개 건너뜀)**. [근거·한계](../../../docs/evidence/04-public-as-is-to-be-comparison.md#반복-예산-보류-수정-실제-입력-토큰으로-후속-관점-예약). 새 소유자 승인·모델 재실측 없이 예전 JSON을 바꾸거나 진단 품질 향상을 주장하지 않는다. 티켓 `open`, v26 범위 유지.

- **동반 폐기 재현(추가 모델·대상 실행 0):** `analyze()`에 한 관점의 적합 후보 1건과 잘못된 출처 ID 후보 1건을 함께 주면 적합 후보 반환도 0, 미검증은 2건이 된다(`model.py:341-353`). 실제 Starlette Git 출처에서 `_screen()`은 개별 `admit()`이 수락하는 후보와 `next_action.oracle` 누락 후보를 함께 받으면 둘 다 폐기·관점 실패로 기록했다(`diagnose_approved.py:31-69`). `admit()`은 각각 유효한 두 후보라도 원인·조건·영향이 같고 행동/분류가 다르면 전체 병합을 `ValueError`로 중단한다(`admission.py:101-124`); 승인 CLI에서 발생하면 결과 JSON 출력 전 종료 2다. 다른 문장으로 쓴 같은 결함은 반대로 별개 ID가 될 수 있다.
- **추가 손실 경계:** 1,000 출력 토큰 상한·JSON/응답 완결성 검사에 실패하면 구조화 후보가 없고, `--response-output`이 없는 직접 진단은 정규화된 제공자 본문도 보관하지 않는다. OAuth의 미완성 응답은 `content=[]`로 정규화되어 부분 텍스트가 남지 않는다(`model.py:123-136,275-295`). 통합 CLI는 원자료를 보존하지만 사용자 `report.md`에는 미검증 후보 건수·원본 위치만 표시하고 봉인된 다섯 JSON에는 이 후보를 넣지 않는다(`check_code.py:119-141`). 최종 비교 코드는 `status != completed`인 군의 예측을 금지해, 유효 후보가 섞인 실패 호출은 현재 채점할 수 없다(`head_to_head.py:205-208`, `paired.py:282-299`).
- **판단·권고(아직 구현/동결 변경 아님):** 승인/원본 Git SHA 불일치·무단 실행은 실행 전체를 거절한다. 다른 파일·미전달 줄·출처 불일치는 **그 후보만** 거절하고 정상 후보는 남긴다. 예산 초과 시 추가 전송을 멈추되 앞서 유효했던 결과는 보존한다. 후보가 가리킨 경로·줄을 먼저 검증하고 파일 출처 ID는 인증된 Git 자료에서 **시스템이 계산**한다. 원래 모델 인용 ID와 계산된 ID를 감사 기록에서 구분한다. 후보별로 수락·미완성·근거 불일치를 격리하고, 추정 행동/시간·복수 분류가 모호하면 `Finding`으로 임의 승격하지 않은 채 사용자에게 별도 미결 가설로 보여준다. 호출 완료와 후보 채택·검증 완료는 서로 다른 상태로 기록한다. 중복·상충 가설은 전체 실행을 중단하거나 강제로 하나로 합치지 않고 독립 기록 후 근거로 대조한다. 현재 프롬프트 문구 수정만으로 이 동반 폐기 구조는 해결되지 않는다.
- **평가 경계:** 위 규칙을 양 군에 동일하게 적용하고 최종 holdout **전에** 변환·부분 결과 채점·중복 판정 규칙을 동결해야 한다. 원시 후보 건수와 접수율/거절 이유, 실행·독립 판정으로 확인된 TP/FP/FN, 미결·실패, 비용을 각각 공개한다. 모델 주장의 위치 증명은 결함 진실이나 실행 확증이 아니다. 이 검토에서는 소스·동결 manifest·평가 코드를 변경하거나 새 승인 호출을 하지 않았다. 티켓 `open`.

### 사용자 이의에 따른 간소화: 먼저 원문 탐지와 접수 결과만 분리

- 위의 ID 정규화·후보별 상태/병합 재설계는 **채택하지 않는다**. 아직 이만한 구현이 필요한지 입증하지 못했고, 새 파이프라인은 또 다른 탈락 조건을 만들 수 있다.
- 우선 기존에 보관된 승인 응답을 **모델 재호출 없이** 같은 기준으로 읽어 `원문에서 알려진 결함을 지적했는가`와 `기존 시스템이 접수했는가` 두 숫자만 나란히 표시한다. 현재 Starlette 개발 사례의 EOF 결함에 한정하면 수정 전 강한 모델은 **원문 1·접수 0**, 작은 모델은 **원문 0·접수 0**이다. 원문 일치 판단은 공개 수정 내용과의 개발용 의미 대조이며 독립 최종 정답이나 소급 접수 결과가 아니다.
- 사용자가 실제 주장을 놓치지 않도록 해야 한다면 첫 제품 변경은 기존 `unverified_candidates`의 **위치·주장만 “미검증”으로 리포트에 표시**하는 것으로 제한한다. 출처·승인·실행 확인 관문과 `findings`는 그대로 둔다. 원문 대비 접수 손실과 사용자 유용성을 본 뒤에만 더 큰 구조 변경을 고려한다. 최종 우월성 평가는 사용 가능한 권고와 독립 정답을 별도로 요구하고, 두 군에 같은 규칙을 적용해 사전 동결한다. 이 재검토는 구현이나 재평가 실행이 아니다.

### 간소화 구현: 기존 결과 대조·미검증 주장 표시

- 새 모델 호출 없이 소유자 전용 Starlette 승인 응답 12건의 바이트 SHA를 결과 참조와 대조하고, 사전 지정한 공개 *다중 Range 조기 EOF 무진전* 한 건만 원문/접수 양쪽에서 비교했다. 수정 전 강한 모델 **1/0**, 작은 모델 **0/0**, 수정 후 강한/작은 모델 각각 **0/0**이다. 수정 후 강한 모델의 *단일* Range EOF 주장은 이 결함에 포함하지 않았다. [네 판본·군 표와 개발용 한계](../../../docs/evidence/04-public-as-is-to-be-comparison.md#원문-탐지와-시스템-접수의-차이-동일한-공개-eof-결함-한-건). 다른 후보의 참/거짓, 독립 최종 정답과 A+은 입증하지 않았다.
- `check_code.py`는 이미 보관하던 `unverified_candidates`의 모델 주장 위치·원인·거절 이유만 `report.md`의 별도 **미검증** 절에 보여 준다. 위치나 주장 형식이 무효하면 내용을 만들어 내지 않고 미제공으로 표시한다. 기존 보고서 텍스트 무해화 처리로 HTML·Markdown을 이스케이프한다. `findings`, 봉인 5종 JSON, 우선순위, 출처·승인 경계, 프롬프트/RunManifest는 변경하지 않았다. 합성 Git/시험 응답으로 실제 통합 CLI 종료 3, 미검증 1건 표시·봉인 0건·HTML 무해화·0700 출력 확인(외부 모델 0). 전체 Python 3.12 회귀 **172개 통과**, 3.14 **172개 실행(171개 통과·1개 건너뜀)**. 이 수정은 새 모델의 탐지력 개선으로 계산하지 않는다.

## 신규 프롬프트 재실측의 승인 전 준비

- 사용자 목표를 A+의 **실측 가능 상태**로 유지한다. 공식 7개 항목 중 비교 품질·최적화·시스템 완성도를 문서나 원시 후보만으로 인정하지 않는다. 먼저 이미 고정한 Starlette 수정 전/후×두 모델을 **새 프롬프트**로 다시 측정할 수 있도록, 이전 네 설정에서 `model.prompt_sha256`만 바꾼 네 RunManifest를 `/tmp/wreckfish-starlette-prompt-v2-prep-20260927/`에 만들었다(디렉터리 0700, 파일 0600). 해시·명령·한도는 [개발 증적](../../../docs/evidence/04-public-as-is-to-be-comparison.md#수정된-프롬프트-재실측-준비-소유자-승인-전)에만 기록한다.
- 두 출처 묶음 `verify_git_source` 통과(각 84개 Python 기록), 네 설정 모두 원설정과 프롬프트 해시 외 일치·`manifest_hash`·`validate_model_plan` 통과. 실제 Python 3.14 `diagnose_approved.py` 네 조합은 새 영수증 부재로 각각 **종료 2**, 응답 보관 디렉터리 0개였다. 새 모델 호출·대상 실행·승인 영수증은 **0건**. 기존 `.used` 네 건은 재사용하지 않는다.
- **미해결 관문:** 소유자의 네 정확한 RunManifest 해시별 대화형 입력과 일회용 영수증, 필요한 동안만 켤 모델 프록시, 결과별 정규화된 제공자 응답 보관이 있어야 새 프롬프트의 실제 접수 변화가 측정된다. 이 정적 개발 비교도 전체 `F_runtime_feedback`이나 독립 80사례·실제 USD·회사 업무·서비스 운영 증거가 아니므로 티켓은 `open` 유지하고 동결 manifest v26은 그대로 둔다.
- 공식 [7개 심사 항목](../../../docs/project-context/ai-professional-evaluation-criteria.md)을 실제 증거와 대조했다. 제안서·KPI·심사 대응표·기술 증적·증적 색인의 활성 계약을 v26으로 통일하고, v25 당시 cgroup **거절**과 v26 개발용 **경고 후 허용**, 후속 승인 Prefect 원본 수학 함수의 수정 전 실패/수정 후 통과를 시점별로 구분했다. 회사 업무 근거·수정 제안서 공식 수용·최종 독립 80사례·USD 청구·서비스 운영 근거가 없으므로 공식 종합 A+을 계산하거나 주장하지 않는다. 이는 문서의 사실 정정이지 새 실험·구현 성과가 아니다.

## 새 프롬프트 네 영수증 소비·공개 개발 실측

- 소유자가 네 설정의 SHA를 본인 대화형 단말에 입력해 발급한 영수증을 각각 `verify_approval()`로 확인했다. 앞서 고정한 Starlette 부모/수정 commit의 추적 Python 각 84개를 `verify_git_source()`로 재대조하고, 루프백 계정 목록에서 두 모델을 확인했다. Python 3.14 `--symbol FileResponse._handle_multiple_ranges`로 수정 전/후 × 강한 단일/작은 5관점을 영수증당 한 번씩 실행했다. 네 영수증 `.used`, 응답 12건의 `response_sha256`·파일 바이트 SHA·0700/0600 권한을 확인한 뒤 루프백 서버를 종료했다. 결과별 상태·SHA·토큰·원문 후보/임시 접수는 [개발 증적](../../../docs/evidence/04-public-as-is-to-be-comparison.md#수정된-프롬프트-소유자-승인-후-네-건-실제-진단)에 기록했다.
- 실제 요청 12회 중 11회 완료·`correctness` 1회 `candidate_ungrounded` 실패. 이 실패 후보의 파일 출처 ID는 맞지만 `taxonomy=concurrency`여서 관점 분류가 불일치했다. 원문 후보 12건·출처/형식 임시 접수 11건·미검증 1건, 제공자 보고 총 124,332토큰이다. 수정 전 강한 모델은 **다중 Range 조기 EOF**의 실제 읽기 루프 `449-452`에 한 임시 접수 후보를 냈다. 작은 모델도 같은 원인을 접수 후보 2건으로 냈으나 위치 `438-440`, `447`은 읽기 루프가 아니고 서로 별개 결함이 아니다. 전체 작은 모델 CLI 종료 3. 수정 후 어느 군도 **그 다중 Range 무진전**을 주장하지 않았다. 다른 원시 후보의 진실성·실행 검증은 미판정이다.
- **결정:** 이번에는 접수 규칙·프롬프트·동결 명세를 다시 변경하지 않는다. 새 모델 호출과 기존 호출 간 차이는 비결정적 재측정이며 향상 인과를 단정할 수 없다. 한 공개 사례·미완성 다관점 실행·실제 USD 청구 부재로 final `F_runtime_feedback` 대 `S_strong_single`의 우월성이나 A+을 주장하지 않는다. 추가 대상 실행·새 호출에는 새로운 정확한 승인과 독립 평가 절차가 필요하므로 티켓은 `open` 유지한다.

## 탐지 실패 원인 심층 분석과 개선 가설 (구현·신규 모델 호출 없음)

### 관측과 반증

- **탐지 실패와 표현 실패를 구분:** 새 프롬프트의 작은 모델 원문 세 후보는 모두 공개 EOF 무진전을 설명했다. 실패 관점의 파일 출처 ID는 맞지만 `correctness`에 `taxonomy=concurrency`를 반환해 `model.py:341-353`의 관점 일치 검사에서 탈락했다. 같은 문제가 정확성·성능·동시성 영향을 동시에 가질 수 있는데, 현 구현은 조사 관점과 결함 분류를 동일시한다. 이 결과를 모델이 원인을 전혀 이해하지 못한 증거로 쓰지 않는다.
- **실제 요청 재구성:** Python 3.14로 고정 Git의 `graph`·`retrieve`·`analyze`를 실행하되 `_request`를 전송 없는 캡처 함수로 대체했다. 네 실행의 첫 요청 SHA가 저장된 감사 SHA와 모두 일치했다. 수정 전 source slice 23,654바이트 중 고유 파일·줄 바이트는 17,185, 중복은 **6,469(27.35%)**; 수정 후 23,934 중 고유 17,325·중복 6,609. 클래스 본문과 메서드가 겹쳐 EOF 읽기 줄도 두 번 포함됐다. `source_slice`는 시작·끝 줄 메타데이터만 있고 줄별 번호는 없다(`code_graph.py:251-275`). 중복 제거만의 품질 개선은 아직 미측정이다.
- **정적 도움의 공백:** 두 판본 모두 실제 전송 문맥의 `static_counterexamples=[]`였다. 현 `counterexamples.py`는 0 나눗셈·빈 인덱스만 다루고 클래스 메서드 이름과 조건부/반복 경로는 분석하지 않는다(`:12-13,69-81,105-118`). 따라서 이 실행에서 그래프는 주변 소스를 제공했지만 EOF 진행 조건을 계산해 주지 않았다.
- **다섯 관점은 추론 단계 분업이 아님:** `analyze`는 같은 문맥·공통 지시문에서 관점 문자열을 바꾸고 앞선 후보를 다음 호출에 전달하지 않는다(`model.py:252-272`). 수정 전 작은 모델의 제공자 사용량은 캐시 포함 입력 48,237·출력 2,346(입력 95.36%), 수정 후 입력 48,782·출력 967(98.06%)이었다. 이는 반복 입력의 크기 관측이며 캐시 할인·USD 낭비율이나 추론 품질의 인과는 아니다.
- **위치·중복 검사의 한계:** 현재 위치 검사는 실제 파일·줄·전송 범위를 확인하지만 해당 줄이 주장한 연산인지 증명하지 않는다. 중복 키는 `root_symbol/mechanism/condition/impact`의 문장 그대로라 동의어로 설명한 EOF가 서로 다른 finding이 된다(`admission.py:23-30,101-124`). 한 결함을 여러 분류로 다시 말한 것을 고유 발견으로 세면 안 된다.
- **출력 제한 가설 반박:** 실제 강한 응답은 출력 2,592/2,005토큰이고 12개 응답은 모두 `end_turn`이다. 설치된 `openai-oauth@2.0.0`의 `@openai-oauth/core/dist/runtime.js:389-403`은 `max_output_tokens`를 삭제한다. 해당 순수 정규화 함수를 소스 없는 입력으로 실행해 `inputLimit=1000`, `outputHasLimit=false`를 확인했다. 따라서 이번 실패를 “1,000토큰에 잘려서 발생”으로 설명하지 않는다. 제공자 기본 reasoning 설정도 프록시가 적용할 수 있으므로, 향후 실험은 요청한 설정과 실제 적용된 설정을 구분해야 한다. 이번 총 토큰은 각 승인 한도 안이었지만 개별 출력 상한 강제는 입증되지 않았다.

### 제안: 분류별 리뷰 대신 가정 파괴와 근거 경로

- **[INFERENCE] 핵심 가설:** 작은 모델에 완성된 버그 보고서를 다섯 번 쓰게 하기보다, 코드가 의존하는 가정 중 깨질 수 있는 것 하나를 고르게 하고 AST가 위치·진행식·탈출 분기를 연결하면 고유하고 정확한 가설을 더 싸게 만들 수 있다. 아직 구현·품질 개선 증거는 없다. 신경망과 정적 분석의 결합 자체를 새로운 발명으로 주장하지 않는다.
- **최소 대상은 반복문의 진행 조건:** `start < end`의 남은 작업 `end-start`와 갱신 `start += len(chunk)`를 AST로 추출한다. 모델은 코드·API 계약을 보고 “파일 크기를 확인한 뒤 파일이 짧아져 read가 빈 바이트를 반환할 수 있는가”를 제안한다. 제한된 경로 검사기는 `chunk=b""`일 때 증가량 0·조건 유지·탈출 부재인지 계산한다. 수정 후 `if not chunk: raise`면 해당 무진전 경로는 차단된다. 실제 두 판본 AST에서 이전 while449/update451/종료 분기 없음, 수정 while449/update453/451의 `not chunk → Raise`를 확인했다. 대상 함수 실행이나 범용 경로 검사기 구현은 하지 않았다.
- **가정의 유효기간을 조사 단위로:** stat/캐시 읽기/권한 확인 시 얻은 사실이 실제 read/쓰기/사용 시점에도 유효한지 묻는다. 외부 변경·부분 반환·취소는 API 계약과 코드의 보호 조건에 근거할 때만 허용한다. `await` 존재나 빈 반환 가능성만으로 결함을 확정하지 않는다. 잠금·불변 객체·정상 재시도·외부 진행 보장·예외 처리 때문에 성립하지 않는 반례는 기각하고, 알 수 없는 호출/경로는 unknown으로 남긴다.
- **역할 분담은 증거를 추가하는 작업:** 한 번의 가정/반례 제안 뒤, 필요할 때만 별도 검토가 잠금·가드·상위 호출의 반대 근거를 찾는다. 동일 주장의 다수결이 아니라 실제로 새 근거를 얻었는지 평가한다. 기본 5관점 경로는 비교군으로 유지하고, 신규 탐색 경로의 이름만 바꿔 최종 F로 주장하지 않는다.
- **먼저 해야 할 작은 개선:** 선택한 소스 구간을 중복 없이 한 번씩 표시하고 줄/AST 문장 앵커를 미리 제공한다. 모델은 숫자 줄을 만들어 내는 대신 주장의 핵심 연산에 해당하는 앵커나 정확한 원문 인용을 선택한다. 시스템이 고정 Git에서 유일한 위치를 확인하고 주장한 연산과의 연결은 따로 검사한다. 앵커 존재는 결함 진실의 증거가 아니다. 분류 오류는 분류 오류로 보여 주고 모델 주장을 재작성해 정답처럼 접수하지 않는다. 거대한 후보 정규화·병합 상태기계는 아직 채택하지 않는다.

### 제안된 대조 실험과 중단 조건

- 이번 Starlette는 이미 답을 본 개발 예시다. 이것만 맞히는 규칙을 만들고 성능 개선이라 주장하지 않는다. 별도 공개 저장소의 수정 전/후 반복문·정상 retry/정상 EOF/가드 사례를 결과 관측 전에 고정하며, 수정판·패치·정답은 진단 입력에서 분리한다. 필요한 모델 전송·대상 oracle 실행은 새 정확한 소유자 승인을 받는다.
- 먼저 동일 작은 모델에서 현 5관점, 같은 문맥의 단일 일반 검토, 중복 제거·앵커만 적용한 검토를 비교해 모델 크기와 입력 표현의 효과를 분리한다. 다음에 가정 파괴 경로를 추가하되 **동일 AST 규칙만 쓰는 비AI 기준선**도 둔다. 이미 단순 규칙이 해결하는 EOF를 LLM 기여로 돌리지 않는다. 모든 검토·추가 검색·실패 비용을 총 예산에 넣고 강한 모델 비교는 별도로 유지한다.
- 기준은 고유 원인+근거 연산 위치+유효 발생 조건+실행 가능한 권고의 일치, 정상/수정 코드 오탐, 누락, unknown/미완료, 전체 토큰이다. 후보 수·접수율만 높아지거나 정상 재시도를 버그로 몰거나 규칙 단독 대비 기여가 없으면 새 구조를 승격하지 않는다. 지표·반복 계획은 호출 전 고정하며 최종 80사례 계약은 변경하지 않는다.

### 외부 근거와 한계

- [IRIS 원 논문](https://arxiv.org/html/2405.17238v1), 2024-05-27: LLM의 API 명세 제안과 CodeQL의 경로 추적을 분리하는 선행 설계. Java 보안 연구이므로 Python EOF 개선 수치로 전용하지 않는다.
- [LLM4PFA](https://arxiv.org/html/2506.10322v1), 2025-06-12: 제한된 경로 제약·문맥 추론을 결합하지만 실제 양성도 놓쳤다고 보고한다. LLM 반증자의 기각은 자동 정답이 아니며 제약 모델이 틀리면 검사도 틀릴 수 있다는 반대 근거다.
- [When and Why Does Multi-Agent Debate Fail](https://arxiv.org/html/2510.20963v2), 2026-07-14 개정: 같은 예산에서 협업 프로토콜에 따라 손익이 달라진다는 연구. 현 시스템은 토론형이 아니므로 직접 성능 비교가 아니라, agent 수 대신 추가 정보의 가치를 측정해야 한다는 설계 근거로만 사용한다.
- [Gordian 초록](https://arxiv.org/abs/2603.19239): 긴 경로의 전역 제약 일관성을 LLM만으로 처리하기 어렵다는 반대 근거. 초록만 확인했으며 구체적 성능·구현 채택 근거로 쓰지 않는다.
- 분석 신뢰도: 코드·원자료·오프라인 재구성 관측 High, 문맥 중복이 오답을 유발한 인과 Low, 새 가정 파괴 방식의 품질/비용 향상은 미측정. 이번 작업은 신규 모델 호출 0·대상 실행 0·제품 코드 변경 0이며 티켓은 open 유지.
- 독립 검토도 분류 탈락·위치 연결 부재·문장 기반 중복 식별을 확인했다. 추가 비교 제약: 강한 모델 단일 모드는 다섯 유효 분류 중 하나면 허용하지만 작은 모델 다관점은 해당 호출 관점과 같아야 한다(`model.py:341-346`). 따라서 모델 크기뿐 아니라 접수 조건도 다르다. 접수 수 차이를 구조의 순수 효과로 해석하지 않으며, 다음 대조에서는 원문과 동일한 평가 규칙에 따른 점수를 함께 비교한다. 이번 결과를 소급 변경하지 않는다.

## 추가 관점으로의 설계 정정

- 사용자는 가정을 굳이 깨뜨리는 방식보다 기존 다섯 관점에 새로운 검토 역할을 추가하는 방향을 제안했다. 앞선 대체 중심 제안은 정정한다. 기존 구조/정확성/성능/동시성/테스트 검토를 유지하고, **가정·경계조건 검토**를 추가 실험 후보로 둔다. 채택·구현·실측 완료를 의미하지 않는다.
- 새 역할은 실제 코드를 변경하거나 결함을 주입하지 않는다. 코드가 기대하는 입력·외부 응답·상태 유지 조건과 이를 보장하는 가드/호출 계약을 대조한다. 반드시 반례나 버그를 만들어 내게 하지 않고, 보장됨/위험 후보/근거 부족을 구분한다. 문제를 깨뜨리는 것은 필수 절차가 아니라 필요할 때 쓰는 사고 방법이다.
- 조사 역할과 결과의 결함 분류는 별개다. 추가 역할에서 발견한 EOF 문제도 기존 correctness/performance/concurrency 분류로 표현할 수 있으므로, 여섯 번째 taxonomy를 자동 신설하거나 기존 관점 일치 검사에 그대로 추가하지 않는다. 분류 계약 변경은 실제 구현 시 명시적으로 설계한다.
- 효과는 기존 다섯 관점 대비 새롭게 확인된 고유 원인·중복·오탐·총 비용으로 평가한다. 기존 다섯 관점에 일반 재검토 한 번을 추가한 같은 예산 대조군도 두어, 역할 효과와 호출 증가 효과를 분리한다. 이름만 다른 전체 코드 재검토는 피하고 구체적인 검토 질문과 근거를 갖게 한다. 이번 정정은 설계 기록뿐이며 모델 호출·대상 실행·제품 코드 변경은 없다.

## v27 추가 검토 역할 구현·검증

- 사용자의 구현 요청에 따라 기본 다섯 역할은 유지하고 개발용 `--boundary-review` 경로를 구현했다. 명시적으로 선택한 실행만 여섯 번째 `assumptions` 검토를 수행한다. 강제 반례·결함 주입·자동 수정을 하지 않는다. 입력/외부 반환/상태/종료 가정을 코드의 가드·호출 계약과 대조하도록 지시하며, 근거 부족은 가설이고 빈 후보는 안전 판정이 아니다.
- `model.py`의 별도 `BOUNDARY_PROMPT_SHA256`은 `59f1c86b482c16481c7f9cec760ada67d443dbed327d0c39d7a153bf67905333`이다. 기본 `PROMPT_SHA256`과 plain 경로는 그대로다. 여섯 요청은 같은 지시문과 문맥에서 역할만 바꾸므로 기존 공유 예산 예약 계산을 유지한다. `perspective=assumptions`는 검토 주체이고 `taxonomy`는 기존 다섯 값만 허용한다. 기존 다섯 역할의 분류 제약과 위치·출처 검사는 그대로이며 의미 중복·줄 인용 개선은 이번 범위에 넣지 않았다.
