## Question

입력 동결→정적 사실→문맥 구성→다관점 가설→정책 승인 동적 검증→근거 판정→위험 병합의 노드·의존성·병렬성·전체 실행 예산·중단 조건·재시도·timeout·partial failure·fixed-five 안전 기준선·deterministic merge를 어떻게 고정할 것인가?

## Resolution comment

기본 DAG는 `snapshot·RunManifest 검증 → 정적 사실·Code Graph → 결정론적 문맥 → 고정 다섯 관점 가설 → 승인된 조건부 실행 → 근거 판정 → 동일 위험 병합·보고서`다. snapshot과 정적 index가 끝나야 문맥을 만들며 다섯 관점은 같은 동결 문맥에서 병렬 수행한다. 각 가설의 동적 검증은 승인된 node의 선행 조건과 가용 예산이 충족될 때만 수행한다. 근거 판정 후 병합은 identity key와 evidence ID를 정렬해 결정론적으로 실행한다. 다섯 관점 중 하나를 조용히 생략하거나 다수결로 `confirmed`로 올리지 않는다.

- 전체 wall time·CPU·memory, token, tool-second, node timeout과 동시 실행 한도는 RunManifest에 포함해 승인한다. 평가 여섯 arm에는 같은 상한을 적용한다. 먼저 최소 정적 보고서를 만들 수 있는 예산을 예약하고 남은 범위에서 동적 node를 수행한다. 계측값과 예산 소진 위치는 ScanRun에 남긴다. 정확한 상한은 파일럿 뒤 동결한다.
- snapshot·hash·승인 불일치, source 부재, 최소 보고서 전 예산 소진은 scan `rejected`로 끝난다. 모델·test·profiler 실패, 승인 거절, node timeout은 해당 가설 `deferred`와 미실행 이유를 남기고 나머지 독립 가설은 계속 처리한다. 최소 보고서 뒤 중단은 `accepted` + coverage 누락이며 누락된 비교는 `unknown`이다. oracle로 기각·확인된 사실은 실패한 다른 node 때문에 뒤집지 않는다.
- 재시도는 같은 승인과 전체 예산 안에서 일시적인 모델·읽기 오류에 한 번만 허용한다. 실행 node 재시도는 RunManifest에 idempotent workload와 횟수가 명시된 경우에만 허용한다. timeout 뒤 프로세스를 중단하고 종료·artifact hash를 기록한다. 승인 범위를 늘리는 재시도는 금지한다.
- 병합은 ticket 011 identity key가 동일할 때만 수행한다. 상충 근거나 해석 불가 경로는 `deferred`; 확인 근거 없는 모델 주장만으로 `confirmed`를 만들지 않는다. 다섯 관점 모두 실행 여부·비용·실패 이유가 trace에 남아야 한다. 기존 ticket 014 조건부 runtime DAG를 변경하지 않는다.

- v27 개발용 추가 경로: 명시적 `--boundary-review`에서는 기존 다섯 역할 뒤에 `assumptions`를 한 번 추가하고, 모든 모듈·여섯 역할이 같은 승인 예산을 공유한다. 여섯 역할의 상태·비용·실패를 기록하며 추가 역할 실패도 해당 개발 실행의 불완전 상태에 포함한다. 기본 다섯 관점·최종 A~F·두 shadow 실험은 그대로이고 새 경로의 결과를 최종 지표에 합산하지 않는다. 추가 역할은 결함 분류가 아니므로 기존 다섯 taxonomy만 사용한다. 상세 구현·검증은 [진행 티켓 029](029.md)에 기록한다.

적용값은 [현장 입력 명세 v22](../field-input-manifest.yaml)의 `analysis_dag_contract`에 기록했다.

v28 후속 적용: 호출 역할은 시스템이 기록하고 taxonomy와 분리한다. 호출 완료와 행 접수도 분리하며, 무효 행만 미검증으로 남긴다. 정확한 동일 원인 키에서 병합 필드가 충돌하면 그 묶음 전체를 격리하고 독립 후보는 보존한다. 미검증 행이 있으면 호출이 모두 완료돼도 개발 분석은 불완전·종료 3이다([029](029.md#v28-p0-구현로컬-검증-완료)).
