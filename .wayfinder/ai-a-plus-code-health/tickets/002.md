## Question

초기 제품의 단 한 명의 1차 사용자는 누구이며, 정기 점검과 RC 점검 결과로 내려야 할 핵심 결정은 무엇이고, 어떤 관찰 가능한 사용자 결과 하나가 개선되면 성공으로 볼 것인가?

## Resolution comment

### 1차 사용자

개인 AI 인증 과제의 프로젝트 책임자이자 Python 백엔드 maintainer인 본인 1명으로 고정한다. 별도 개발자·리뷰어 집단의 성과로 일반화하지 않는다.

### 제품이 지원하는 핵심 결정

- **정기 main 점검**: 현재 위험 중 다음 점검 주기 전에 가장 먼저 검증할 대상 1개, 그 근거, 다음 검증 행동을 확정한다.
- **릴리스 후보 점검**: `main` 대비 후보 commit에서 새로 생기거나 악화된 위험 중 사람의 릴리스 판단 전에 가장 먼저 검증할 대상 1개, 그 근거, 다음 검증 행동을 확정한다.
- 시스템은 다음 검증 우선순위만 제안한다. 코드 수정, merge, 릴리스 승인·보류·차단은 사용자가 결정한다.

### 자동 평가 성공 결과

사람 평가를 사용하지 않는다. `ValidNextVerificationRecommendation@20m`을 유일한 제품 1차 결과로 사용한다.

```text
ValidNextVerificationRecommendation@20m
= 전체 pipeline이 20분 안에 유효한 다음 검증 권고를 만든 case 수
  / 동결된 최종 case 80개
```

Manual/Assisted 사람 비교를 폐기하고 같은 80개 case에서 다음 두 arm을 paired 비교한다.

- baseline: `A_plain_llm`
- proposed: `F_runtime_feedback`

proposed 완료율이 baseline보다 **30%p 이상 높고**, repository/template family 단위 95% bootstrap 신뢰구간의 차이 하한이 0보다 크며, proposed의 Critical/High 부당 기각이 **절대 0건**이면 성공이다.

### 유효한 권고의 동결 조건

1. 선택한 위험이 사전에 봉인한 허용 최우선 위험 집합에 포함된다.
2. 근거가 해당 source snapshot과 일치하고 위험 가설을 실제로 지지한다.
3. 다음 행동이 가설을 확인하거나 반박할 관찰과 연결된다.
4. 실행 행동은 정확한 대상·workload·판정 oracle을 가진다. 실행 불가 사례는 올바른 판단 보류만 유효하다.
5. 알려진 Critical/High 위험을 근거 없이 기각하지 않는다.

판정은 실행 oracle을 우선하고, 고정된 독립 LLM judge는 위험·근거·다음 행동의 의미 일치만 판단한다. judge는 arm 정보를 받지 않으며 실행 oracle을 뒤집을 수 없다.

### 측정 경계

- 80개 case 모두 baseline과 proposed를 실행한다.
- 두 점검 모드와 두 final 자료 lane 조합에 각각 20개를 배치한다.
- 20분은 정적 분석, LLM, test·profiler를 포함한 전체 machine wall time이다.
- 시간초과, 중단, tool 오류, judge 오류, 무효 권고는 분모에서 삭제하지 않고 실패로 센다.
- 공개 파일럿은 절차 조정에만 쓰고 최종 분모에서 제외한다.

### 1차 결과와 분리할 기술 증거

Recall·Precision·Critical/High Recall, runtime confirmation, profiler coverage, context evidence Recall, token·tool 비용, component ablation은 별도 품질·기술 지표로 보고한다. 사람 의사결정 시간, 사람 재작업, reviewer 생산성 향상은 측정하거나 주장하지 않는다.
