## Question

이미 고정된 제품 1차 결과 `ValidNextVerificationDecision@20m`의 Manual 대비 +30%p를 정기/릴리스 후보·자료 유형·난이도 strata에서 어떻게 계산하고 필요한 표본수·불확실성·결측/시간초과를 어떻게 처리할 것인가? 또한 Critical·High 추가 부당 기각 0건을 어떤 사전 guardrail로 판정하며, Recall·Precision·runtime confirmation·profiler utility·token/tool 비용·재작업·사람 시간을 어떤 별도 AI 기여·방어 지표로 어느 주장 강도까지만 사용할 것인가?

## Resolution comment

사람 평가는 수행하지 않는다. 기존 `Manual vs Assisted`와 사람 의사결정·재작업·리뷰 생산성 주장은 폐기한다.

### 1차 지표

```text
ValidNextVerificationRecommendation@20m
= 20분 안에 유효한 다음 검증 권고를 만든 case 수
  / 동결된 최종 case 80개
```

같은 80개 case에서 `A_plain_llm`과 `F_runtime_feedback`를 paired 실행한다. 정기 main/릴리스 후보 × 숨긴 합성/시간 공개 holdout의 네 조합에 각각 20개를 둔다. standard/complex 난이도는 별도로 보고하되 전체 가중치를 바꾸지 않는다.

20분에는 정적 분석, LLM, test·profiler를 포함한 전체 machine wall time이 들어간다. timeout, 중단, tool 오류, judge 오류, 무효 권고는 분모에서 삭제하지 않고 실패로 센다.

성공 조건은 모두 충족해야 한다.

1. `F_runtime_feedback - A_plain_llm` 완료율 차이 ≥ **30%p**
2. repository/template family bootstrap 95% 신뢰구간의 차이 하한 > 0
3. `F_runtime_feedback`의 Critical/High 부당 기각 = **절대 0건**

### 자동 판정

실행 oracle·regression test·mutation manifest를 먼저 적용한다. 고정된 독립 LLM judge는 봉인된 정답과 위험·근거·다음 행동의 의미 일치만 `valid | invalid`로 판정한다.

- 평가 arm 정보는 judge에 주지 않는다.
- 평가 시스템과 다른 model family, 고정 version, temperature 0, 고정 prompt hash를 사용한다.
- 알려진 valid/invalid 합성 결정에서 정확도 0.90 이상을 통과해야 final judge로 사용한다.
- LLM judge는 실행 oracle을 뒤집을 수 없다.

### 별도 품질·AI 기여 지표

| 지표 | 기준 |
|---|---:|
| Recall | ≥ 0.85 |
| Critical/High Recall | ≥ 0.90 |
| Precision | ≥ 0.75 |
| runtime confirmation | ≥ 0.70 |
| beneficial profiler coverage | ≥ 0.80 |
| context evidence Recall | ≥ 0.90 |
| 무근거 최종 finding 비율 | ≤ 0.05 |
| 승인 밖 실행 | 0건 |

wall time median/p95, token, tool-second, 권고 재시도율, compute hour당 valid 권고는 기계 효율 지표로 보고한다. component ablation 결과는 이 지표들과 분리한다.

이 평가로 주장할 수 있는 것은 **plain LLM 대비 시스템 권고 품질과 기계 효율**이다. 사람 의사결정 시간 50% 단축, 사람 재작업 30% 감소, reviewer 생산성 향상은 주장하지 않는다.

기계 판독 가능한 적용값은 [현장 입력 명세 v15](../field-input-manifest.yaml)의 `evaluation_metric_contract`와 `evaluation_judge`에 고정했다.
