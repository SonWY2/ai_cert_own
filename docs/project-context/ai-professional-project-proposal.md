## 2. 과제 정의

### 2.1 대상

- 코드 품질 개선을 위해 개발 과정에서 발생하는 코드 품질·성능 리스크를 진단하고 분석하는 에이전트 구축
- 주요 대상은 Python 기반 백엔드 서비스, API 처리 흐름, 비동기 처리 로직, 테스트가 부족한 복잡 모듈
- 적용 상황은 구현 전 검토, PR 전 점검, 장애 의심 구간 분석, 성능 병목 의심 구간 분석을 포함
- 개발자와 리뷰어가 코드 수정 전에 구조적 문제, 버그 가능성, 성능 저하 요인을 빠르게 파악하는 것을 목표로 함

### 2.2 선정 배경

- 코드 품질 문제는 단순 문법 오류보다 구조, 책임 분리, 예외 처리, 동시성, 성능 병목이 복합적으로 얽혀 발생하는 경우가 많음
- 기존 방식은 개발자가 코드, 테스트, 로그, 실행 결과를 개별적으로 확인하며 원인을 추적하는 방식에 의존
- 특히 성능 문제는 코드만 읽어서는 병목 지점을 판단하기 어렵고, 실행 검증이나 profiler 분석이 함께 필요함
- 그러나 실제 개발 현장에서는 시간 부족으로 인해 정적 코드 리뷰에 머무르거나, 문제가 발생한 뒤에야 성능 분석을 수행하는 경우가 많음
- 이에 코드 진단, 실행 검증, 선택적 profiler 분석을 하나의 에이전트 워크플로우로 연결해 개발 초기부터 품질·성능 리스크를 체계적으로 식별하고자 함

### 2.3 Pain point

- **진단 기준의 부재**
  - 코드 품질을 볼 때 구조, 정확성, 성능, 동시성, 테스트 관점이 사람마다 다르게 적용됨
  - 리뷰어 경험에 따라 결과 품질 편차가 발생함

- **정적 분석 중심의 한계**
  - 코드만 읽어서는 실제 실행 경로, 예외 상황, 병목 지점을 확신하기 어려움
  - 성능 저하 원인이 추정 수준에 머무르는 경우가 많음

- **성능 분석의 높은 진입 장벽**
  - profiler 실행, 결과 해석, 병목 함수 식별은 별도 경험이 필요한 작업임
  - 일반 개발자는 성능 이슈가 의심되어도 분석을 후순위로 미루기 쉬움

- **반복적인 수작업**
  - 관련 파일 탐색, 호출 흐름 정리, 테스트 실행, 결과 해석을 사람이 매번 반복 수행
  - 문제 원인 파악까지 시간이 오래 걸리고, 후속 조치 우선순위가 늦게 결정됨

### 2.4 평가 지표

- **진단 소요 시간**: 코드 품질·성능 리스크를 1차 정리하는 데 걸리는 시간
- **리스크 식별률**: 구조, 버그, 성능, 동시성, 테스트 관련 주요 위험 요인 발견 비율
- **실행 검증 연계율**: 진단 결과 중 테스트 또는 실행 결과로 확인된 항목 비율
- **Profiler 활용률**: 성능 의심 구간에서 profiler 분석이 수행된 비율
- **재작업 감소율**: 뒤늦게 발견된 품질·성능 문제로 인한 수정 반복 감소율
- **리뷰 생산성**: 리뷰어가 동일 범위의 코드를 검토하는 데 필요한 시간 절감률

## 3. 개선 계획

### 3.1 개선 방법

- **AI 코드 진단 에이전트 도입**
  - 기존에는 별도 AI agent 없이 개발자가 파일 탐색, 코드 흐름 이해, 테스트 실행 여부 판단, 성능 의심 구간 파악을 수작업으로 수행
  - 개선 후에는 AI agent가 입력된 코드 범위를 분석하고, 주요 위험 요인을 관점별로 분류하여 진단 리포트를 생성

- **5관점 기준선과 적응형 진단 계획 구성**
  - 구조, 정확성, 성능, 동시성, 테스트를 공통 진단 taxonomy와 fixed-five 기준선으로 유지
  - Diagnosis Planner가 AST·Code Graph·변경·증상 근거를 보고 관점별 `run | skip | defer | shadow`와 focus lens를 제안
  - 초기에는 5관점을 모두 실행하는 shadow 평가로 누락 위험을 측정하고, 중요 결함 Recall을 유지한 경우에만 선택 실행으로 승격

- **가설 중심 실행 검증 연계**
  - 위험 주장을 발생 조건, 지지·반박 관찰, 독립 판단 기준이 있는 `HypothesisContract`로 구조화
  - 확인이 필요한 가설은 focused test 또는 좁은 실행 명령으로 검증하고 `확인 | 기각 | 판단 보류`로 구분

- **Python profiler 분석 opt-in 적용**
  - 성능 병목, 느린 API, 반복 I/O, 비효율적인 루프, 비동기 처리 지연이 의심되는 경우 profiler 분석을 선택적으로 실행
  - agent가 profiler 필요성을 제안하고 사용자 확인 후 실행 가능
  - 사용자가 명시적으로 요청한 경우에도 profiler 분석을 직접 실행 가능

- **진단 리포트 표준화**
  - 분석 결과를 자유 서술이 아니라 범위, 위험도, 근거, 영향, 권장 조치 형태로 정리
  - 개발자와 리뷰어가 후속 수정 우선순위를 빠르게 결정할 수 있도록 구성

### 3.2 개선 목표

- **진단 소요 시간 단축**: 수작업 분석 대비 50% 이상 절감
- **성능 병목 탐지 강화**: 코드 리뷰만으로 놓치기 쉬운 병목 후보를 profiler 기반으로 식별
- **리뷰 품질 표준화**: 리뷰어별 편차를 줄이고 공통 진단 관점을 적용
- **재작업 감소**: 뒤늦게 발견되는 품질·성능 이슈로 인한 반복 수정 30% 이상 감소
- **개발 생산성 향상**: 개발자가 문제 원인 탐색보다 실제 개선 작업에 더 많은 시간을 투입하도록 지원

## 4. AI기술 활용

### 4.1 활용 계획

- **LLM 기반 코드 이해 및 위험 요인 분류**
  - AI agent가 입력된 코드 범위와 관련 파일을 분석해 주요 실행 흐름을 파악
  - 구조적 문제, 버그 가능성, 성능 저하 요인, 동시성 위험, 테스트 공백을 관점별로 분류

- **증거 기반 진단 계획 자동 생성**
  - 큰 모듈이나 여러 파일이 연결된 흐름은 먼저 분석 단위로 분해
  - 어떤 파일·함수·테스트·실행 경로와 관점을 확인할지 근거 ID·예산·중단 조건과 함께 제안
  - 기존 5관점은 공통 taxonomy와 실패 시 fallback으로 유지하며, 추가 요구는 `change-impact`, `resource-lifecycle`, `data-transaction-contract` 같은 등록 focus lens로 제한

- **반증 가능한 가설과 실행 검증**
  - 추정만으로 판단하기 어려운 항목은 claim quantifier, 발생 조건, 지지·반박 관찰, 독립 oracle을 실행 전에 고정
  - focused test·profiler 결과를 가설과 연결해 확인·기각·판단 보류 상태로 반영

- **Python profiler 기반 심화 분석**
  - 성능 이슈가 의심되거나 사용자가 요청한 경우 profiler를 opt-in 방식으로 실행
  - 호출 시간, 누적 실행 시간, 반복 호출, 병목 함수 후보를 분석해 성능 개선 후보를 도출
  - profiler 분석은 기본 실행이 아니라 비용과 시간이 필요한 심화 분석 단계로 운영

- **업무 연결 방식**
  - 진단 결과는 PR 리뷰, 리팩터링 계획, 성능 개선 작업의 입력으로 활용
  - 단순 “문제 있음”이 아니라 “어디를 먼저 고쳐야 하는지”를 판단할 수 있는 실행 가능한 결과물로 연결

### 4.2 최적화 계획

- **관점·가설 계약 표준화**
  - 5관점의 책임, `DiagnosisPlan`, `HypothesisContract`, Finding 출력 형식을 version으로 고정
  - 동일 유형 코드의 진단 일관성과 선택 관점의 누락·비용을 함께 측정

- **적응형 관점 선택 최적화**
  - fixed-five를 기준선으로 두고 Planner 제안만 기록하는 shadow arm과 실제 선택 실행 arm을 단계적으로 비교
  - Critical/High 누락, 전체 Recall, 무근거 finding, token·호출 수를 같은 전체 실행 예산에서 검증한 뒤 승격

- **Profiler 실행 조건 최적화**
  - 모든 진단에 profiler를 붙이지 않고, 성능 리스크가 있거나 사용자가 명시적으로 요청한 경우에만 실행
  - 분석 비용과 진단 속도의 균형을 유지

- **결과 해석 자동화**
  - profiler raw output을 그대로 전달하지 않고, 병목 후보와 개선 방향 중심으로 요약
  - 개발자가 바로 후속 조치할 수 있도록 영향도와 우선순위를 함께 제시

- **피드백 기반 개선**
  - 실제 리뷰에서 유용했던 진단, 누락, 오탐을 evaluator-owned label로 수집
  - AI가 실패를 retrieval·graph·관점 선택·추론·병합·검증 단계로 offline 분류하고 변경안을 제안
  - 자동 변경하지 않고 frozen regression, shadow 평가, 사람 승인과 rollback을 통과한 version만 반영

- **운영 안정성 확보**
  - 실행 검증과 profiler 분석은 opt-in으로 운영해 불필요한 비용과 시간을 방지
  - 외부 서비스 의존, 긴 실행 시간, 상태 변경 가능성이 있는 명령은 사용자 확인 후 수행하도록 제한
