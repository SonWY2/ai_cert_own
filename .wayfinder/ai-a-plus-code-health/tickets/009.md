## Question

초기 약속이 적용될 Python·framework·저장소 및 변경 규모·monorepo·async·multiprocess·native·동적 구문 범위와 책임질 코드 건강 위험 taxonomy는 어디까지이며, 경계 밖 입력을 거절·degraded·판단 보류 중 어떻게 표시할 것인가?

## Resolution comment

초기 입력 범위는 **Python 코드가 있는 모든 Git 저장소**로 한다. 특정 framework로 입력을 제한하지 않는다. 다만 A+ 성과 주장은 현재 평가 자료가 대표하는 Python backend·FastAPI·asyncio 범위에만 적용한다.

### 지원 경계

- immutable snapshot에서 발견되는 Python 파일을 정적으로 분석한다.
- monorepo에서는 Python 파일과 정적으로 해석되는 Python 의존 관계만 본다. 다른 언어의 의미 분석은 하지 않는다.
- async·thread·multiprocessing·DI·reflection·dynamic import·monkey patch·native extension이 있어도 저장소를 거절하지 않는다. 해석하지 못한 edge만 `unknown`으로 남기고 영향받는 finding을 `deferred`로 둔다.
- 실행 가능한 workload가 있으면 승인된 RunManifest로 동적 검증한다. workload가 없어도 정적 scan은 유효하다.
- 저장소 크기 보편 한계는 지금 만들지 않는다. 파일럿 실측 전에는 규모 성능을 주장하지 않고, 최소 보고서를 만들기 전에 실행 예산이 끝난 경우에만 scan을 거절한다.

### 상태

scan 상태는 `accepted | rejected` 두 개만 둔다. 별도 `degraded` 상태는 만들지 않는다.

- `rejected`: immutable snapshot 없음, Python source 없음, 최소 보고서 전 분석 예산 초과
- `accepted`: 그 밖의 Python 저장소. 일부 경로를 해석하지 못해도 scan 자체는 accepted

finding 상태는 `confirmed | rejected | deferred` 세 개만 둔다.

- `confirmed`: 해당 주장에 필요한 정적 또는 실행 oracle을 충족
- `rejected`: 반대 증거로 가설이 깨짐
- `deferred`: 동적 경로·실행 환경·근거 부족으로 판단할 수 없음

### 위험 분류

기존 제안서와 같은 다섯 관점만 사용한다.

1. `structure`
2. `correctness`
3. `performance`
4. `concurrency`
5. `tests`

하위 taxonomy는 만들지 않는다. finding 하나에는 주 분류 하나만 지정한다. 코드 위치, 실패 또는 비용 발생 원리, 근거, 다음 검증 행동이 없는 일반적인 모범 사례·style·formatting 지적은 finding으로 받지 않는다.

기계 판독 가능한 적용값은 [현장 입력 명세 v6](../field-input-manifest.yaml)의 `product_scope`와 `support_envelope`에 고정했다.
