## Question

두 모드가 각각 답할 사용자 질문, trigger·freshness, 불변 source/target SHA와 merge-base·수용 baseline, full/delta 범위, new·worsened·improved·resolved·reopened·unknown 의미, 권고·gate 권한과 override 주체를 어떻게 다르게 고정할 것인가?

## Resolution comment

점검 모드는 두 개만 둔다.

### 정기 main 점검

- 매주 한 번 또는 사용자가 직접 호출한다.
- 현재 `main`의 immutable SHA를 저장소 전체 점검한다.
- 직전 성공한 정기 점검 SHA와 비교한다.
- 같은 SHA를 이미 점검했으면 다시 실행하지 않는다.
- 첫 실행은 현재 위험 목록만 만들고 모든 finding을 `new`로 오인하지 않는다.

사용자 질문은 “현재 main에서 우선 확인할 위험은 무엇이며 지난 점검 이후 무엇이 달라졌는가?”다.

### 릴리스 후보 점검

- 사용자가 후보 commit 또는 PR을 지정할 때 실행한다.
- `base`는 main과 후보의 merge-base, `target`은 immutable 후보 SHA다.
- 실행할 때 `scope=impact | full` 중 하나를 선택한다.
  - `impact`: 변경 Python 파일과 Code Graph로 연결된 영향 범위
  - `full`: 저장소 전체 Python 범위
- base 증적이 없으면 같은 실행에서 base를 같은 scope로 분석한다.

사용자 질문은 “이 후보가 새로 만들거나 악화한 위험 중 무엇을 먼저 검증해야 하는가?”다.

### 비교 상태

다섯 개만 사용한다.

| 상태 | 의미 |
|---|---|
| `new` | base에 없고 target에 있음. 과거 이력상 reopened여도 pair 비교에서는 new |
| `worsened` | 같은 finding의 severity 또는 관찰된 영향이 증가 |
| `resolved` | 완전한 target 분석에서 더 이상 발견되지 않음 |
| `unchanged` | 같은 finding이 남아 있고 악화되지 않음. 일부 개선도 여기에 포함 |
| `unknown` | 분석 누락 또는 finding identity 불확실성으로 비교 불가 |

별도 `improved`와 `reopened` 상태는 만들지 않는다. 모든 보고서는 시간 대신 base·target SHA에 묶는다. force-push로 target SHA가 바뀌면 새 실행이다.

시스템은 위험 우선순위와 다음 검증 행동만 권고한다. 릴리스 차단·승인 권한은 갖지 않으며 최종 판단과 무시는 사용자에게 있다.

기계 판독 가능한 적용값은 [현장 입력 명세 v7](../field-input-manifest.yaml)의 `git_topology`에 고정했다.
