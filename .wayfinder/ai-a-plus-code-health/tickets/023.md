## Question

어떤 source 범위, changed-contract test, 두 점검 모드 end-to-end trace, 승인 거절·partial·timeout trace, immutable provenance, primary·guardrail 결과, 독립 기여 evidence, 안전·SLO·보존·rollback 증거와 제3자 재현 절차가 모두 있어야 ‘설계 완료’가 아닌 ‘기본 기능 구현·실증 완료’를 선언하며, 미달 주장은 어떻게 강등할 것인가?

## Resolution comment

`설계 확정`, `기본 기능 구현`, `파일럿 실증`, `최종 성과 검증`을 별도로 판정한다. 이 티켓과 manifest를 닫아도 **설계 확정**일 뿐 구현이나 A+ 달성이 아니다.

| 판정 | 필수 증거 | 부족하면 |
|---|---|---|
| 기본 기능 구현 | 실제 source에서 두 모드의 immutable SHA 입력, 정적 사실·최대 2-hop 문맥, 고정 다섯 관점, 증거 판정·우선순위표, 승인형 pytest/asyncio/cProfile 경로와 다섯 JSON 근거 객체가 연결됨. 변경된 계약마다 소비자 관점 test가 있으며 정상·실패 trace가 재현됨 | 설계 또는 부분 구현 |
| 파일럿 실증 | Python 3.14 합성 fixture와 승인된 두 runtime 파일럿의 version·license·image digest·workload·oracle, Langflow 정적 규모 검사; main full, 후보 impact/full, 승인/거절, no-run, timeout, partial, cache 불일치와 clean replay를 각각 실제 trace로 제시 | 구현만 인정 |
| 최종 성과 검증 | 동결된 80개 paired final case의 두 lane별 결과, 동일 예산 여섯 arm과 두 shadow 실험의 별도 결과, 사전 등록 KPI·guardrail·family bootstrap CI 및 원자료·독립 judge 교정 로그·제3자 재현 명령 | 파일럿까지만 인정 |

모든 trace는 `runs/{run_id}`의 `run.json`, `evidence.jsonl`, `findings.jsonl`, `report.json`, `actions.jsonl`에서 시작해 snapshot SHA, manifest 승인 hash, exact command, 모델·prompt·예산 hash, 실행 artifact까지 검증할 수 있어야 한다. 인증 정보는 포함하지 않는다. 승인 밖 실행 0건, SHA 불일치 거절, 부분 실패의 `deferred/unknown`, 결정론적 병합과 사용자 처분의 append-only를 실제로 확인한다. 보고서에는 성능 p50/p95·peak RSS·cache 동등성, 자원 한도·중단 처리, 근거 보존과 새 manifest version을 통한 rollback trace를 포함한다.

제3자는 의존성 잠금과 image digest를 사용해 동결 case·명령·oracle로 대표 trace와 집계를 다시 생성할 수 있어야 한다. 공개 pilot은 예비 결과로만 표시한다. final holdout의 기준 미달, Critical/High 부당 기각, unsafe 실행, 원천 hash 오류, 숨긴 정답 노출은 성공 주장에 포함하지 않는다. 개인 과제에서는 실사용자 의사결정 시간·재작업 감소와 비공개 기업 사례 일반화를 주장하지 않는다. 공식 A+ 등급은 심사 결과가 없는 한 보장하지 않는다.

적용값은 [현장 입력 명세 v22](../field-input-manifest.yaml)의 `completion_gates`에 기록했다.
